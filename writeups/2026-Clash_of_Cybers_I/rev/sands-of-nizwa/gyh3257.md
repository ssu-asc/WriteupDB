# sands_of_nizwa

## 문제 설명
> Deep beneath Nizwa lies an ancient digital vault. It does not verify the key all at once—it remembers every step. Each correct move reveals the path forward, while one mistake leads deeper into the mirage.
>
> Analyze the binary using Ghidra, understand its verification mechanism, and recover the correct key.
>
> The humbleness of letters is the key to access.

## 풀이

### 분석

`file` 결과 stripped, PIE, x86-64 ELF 바이너리. Ghidra로 디컴파일하면 `main`(`FUN_00101160`)은 단순히 `fgets`로 키를 입력받고, 안티디버그 체크(`FUN_001015c0`, `/proc/self/status`의 `TracerPid` 확인)와 함께 `FUN_001013e0(input, len, is_traced)`를 호출해 참이면 `"THE VAULT OPENS"`를 출력한다.

실제 검증 로직은 `FUN_001013e0` 안에 있는데, 디컴파일 결과만으로는 이해하기 어려운 커스텀 바이트코드 VM 형태였다. 그래서 `objdump -d`로 원본 어셈블리를 직접 추적했다.

핵심 구조:

- `.rodata`의 `DAT_001020e0`에 11(round) × 15(byte) = 165바이트짜리 "바이트코드 테이블"이 존재한다.
- `FUN_00101360(round, pos, key)`는 `(round, pos)`로 테이블을 인덱싱하고, `key`의 특정 1바이트(`pos & 3`로 선택)를 회전/XOR 섞어서 opcode 1바이트를 "복호화"해서 돌려준다.
  ```
  partA  = (round*0x27 + pos*0x13) & 0xff ^ table[round*15+pos]
  keyb   = (key >> ((pos&3)*8)) & 0xff
  raw    = (0x3d*pos + keyb) & 0xff
  rot    = ((pos % 7) + 1) & 7
  opcode = partA ^ rotl8(raw, rot)
  ```
- `key`(=`r10d`)는 **라운드 시작 시점에 고정**되고, 그 라운드가 끝날 때만 그 라운드 동안 누적된 해시 값(`0x97` opcode)으로 갱신된다. 즉 한 라운드 안에서는 opcode 디코딩이 입력값과 무관하게 100% 결정론적이다.
- 라운드 0의 `key`는 안티디버그 체크 결과에서 유도되는데, `TracerPid == 0`(디버거 없이 정상 실행)인 경우 `key = 0xC0DEC0DE`로 **고정 상수**다. (변수명이 `C0DEC0DE`인 것에서 알 수 있듯 의도된 이스터에그.)
- opcode 종류는 8개뿐이다: `0xc3`(누산기+=operand), `0xa1`(입력[operand] 읽기, 길이 초과시 실패), `0xb2`(누산기 ^= key의 특정 바이트), `0xd4`(누산기 좌회전), `0xe5`(누산기 ^= operand), `0xf6`(operand == 누산기 비교, 실패 플래그에 AND), `0x97`(입력바이트·누산기·key·operand를 섞어 다음 라운드 key 생성), `0x00`(라운드 종료). 그 외 값이 나오면 즉시 `return 0`.
- 11라운드를 모두 통과한 �에 최종 key가 `0x47EC6547`이고 길이가 11이면 성공.

즉, "라운드 키가 fixed일 때 opcode 시퀀스는 완전히 결정론적"이라는 성질 덕분에, **틀린 입력 바이트는 거의 항상 다음 라운드에서 잘못된 opcode(위 8개 값 이외)를 만나 즉시 실패**한다. 이 성질을 이용하면 순수 파이썬 백트래킹만으로 빠르게 풀 수 있다 (angr로 직접 심볼릭 실행을 시도했지만, opcode 디코딩 자체가 심볼릭 값에 의존하는 구조라 상태 폭발이 발생해 5회 자동 파이프라인 시도는 모두 실패했다).

### 풀이 과정

1. `objdump -d`로 `FUN_00101360`, `FUN_001013e0`의 정확한 레지스터 흐름을 추적해 위 VM 구조를 재구성.
2. `.rodata`에서 165바이트 바이트코드 테이블을 추출.
3. 안티디버그 우회 없이 정상 실행 기준 라운드0 key(`0xC0DEC0DE`)를 계산.
4. 위 opcode 명세를 그대로 파이썬으로 재구현(`solve.py`).
5. 길이 11, 각 바이트를 미확정(`None`) 상태로 두고 VM을 실행하다가 `0xa1`/`0x97`에서 아직 모르는 입력 위치를 요구하면 해당 위치에 대해 출력 가능 문자(0x20~0x7e)를 하나씩 대입하며 재귀 백트래킹. 틀린 문자는 보통 다음 라운드에서 1~2번 opcode 페치 만에 실패하므로 탐색이 매우 빠르게 끝난다(수백 회 호출 이내).
6. 결과로 `1940{B2211}`를 획득, 실제 바이너리에 입력해 `THE VAULT OPENS` 확인.

## 배운 점

- 커스텀 VM/바이트코드 크랙미는 opcode "페치" 함수가 런타임 상태(키/해시)에 의존하도록 만들어, 정적 디스어셈블만으로는 실제 명령어 시퀀스를 알 수 없게 하는 자기복호화(self-decoding) 기법을 쓸 수 있다.
- 이런 구조는 angr 같은 심볼릭 실행기에 그대로 넣으면 모든 opcode 비교마다 상태가 갈라져 상태 폭발이 일어나기 쉽다. 하지만 "키가 라운드 단위로만 갱신되고 각 라운드 안에서는 결정론적"이라는 설계상의 성질을 파악하면, 라운드별로 concrete 시뮬레이션 + 오탐 조기 실패를 이용한 백트래킹만으로 충분히 빠르게 풀 수 있다.
- Ghidra 디컴파일 결과(특히 인자 없이 호출되는 것처럼 보이는 함수, 부호/상수 표현 등)는 실제 어셈블리와 다르게 보일 수 있으므로, 로직이 복잡한 VM류 문제는 `objdump -d`로 레지스터 흐름을 직접 검증하는 것이 안전하다.
