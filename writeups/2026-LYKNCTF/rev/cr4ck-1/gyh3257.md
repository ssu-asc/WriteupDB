# Cr4ck 1

## 문제 설명
> Cr4ck Cr4ck Cr4ck

Windows GUI KeygenMe (PE32+ x86-64).  
올바른 Username과 License Key를 입력하면 플래그를 표시한다.

## 풀이

### 분석

바이너리를 Ghidra로 디컴파일하면 4단계 검증 구조가 드러난다.

**1단계 – Username 계산 (`FUN_140001f10`)**

RC4 KSA를 키 `L0i_Y3u_Kh0_N0i`로 수행해 256바이트 S-box를 생성한다. 이후 S-box의 특정 인덱스 값과 `.rdata`에 저장된 XOR 마스크(`DAT_1400063f0`, `DAT_140006260`)를 조합해 예상 username을 계산한다.

**2단계 – License Key 생성 (`FUN_1400017b0`, `FUN_140001660`)**

Username을 입력으로 받는 커스텀 해시 함수를 실행한다:
- 초기 상수: `0xa5a5f00d`, `0xae054fb9`, `0x43544632`, `0x4c594b4e ^ (debug_flag * 0x1010101)`
- 3회 반복 루프 + rotl32 기반 혼합
- 출력 4개의 uint32에서 48-bit 부분 추출 → 5그룹 × 4자리 16진수 형식

**3단계 – Anti-Debug (`bVar28`)**

PEB BeingDebugged, NtGlobalFlag, `NtQueryInformationProcess` (ProcessDebugPort, ProcessDebugFlags) 검사. `bVar28 != 0`이면 해시 입력에 영향을 줘 키 파생이 실패한다.

**4단계 – 플래그 복호화 (자가 해시 검증)**

올바른 크리덴셜이 통과된 뒤, SHA256 체인으로 플래그를 복호화:
```
H_text = SHA256(.text section)
H1     = SHA256(username || 0x1f || license_key || 0x1f || H_text || 0x00)
keystream = SHA256(H1||[0,0,0,0]) || SHA256(H1||[1,0,0,0]) || SHA256(H1||[2,0,0,0])
flag   = encrypted_data (DAT_140006280) XOR keystream
```
SHA256 첫 8바이트가 `0x2679dda8691cb57d`와 일치하지 않으면 "vault stays locked" 메시지가 표시된다.

### 풀이 과정

**Step 1 – S-box 구성**

RC4 KSA 변형을 Python으로 재현한다. 첫 번째 스왑은 `S[0] ↔ S[S[0] + KEY[0]]`로 시작하는 특수 형태다.

**Step 2 – Username 복원**

S-box에서 인덱스 `0x1f, 0x24, 0x29, 0x2e, 0x33, 0x38, 0x3d, 0x42`의 값을 big-endian으로 연결 후 `DAT_1400063f0`과 XOR → `th3_LYKN_v3nd0r`

**Step 3 – License Key 계산**

커스텀 해시 함수를 시뮬레이션 후 출력 uint32 네 개로부터:
- `(a>>16)`, `(a^b)&0xffff`, `(b>>16)`, `(d^c)&0xffff`, 체크섬

→ `7211-57C4-CD96-CC26-5B67`

**Step 4 – 플래그 복호화**

`.text` 섹션 SHA256 → H1 → 96바이트 keystream → XOR 복호화

## 배운 점

- RC4 KSA 변형 식별: 첫 번째 스왑이 키의 첫 바이트를 초기 j로 사용
- Self-hash 기반 플래그 암호화: .text 섹션 무결성 검증 + 키 파생을 동시에 수행
- Anti-debug 우회 없이 정적 분석으로 모든 값을 재계산
