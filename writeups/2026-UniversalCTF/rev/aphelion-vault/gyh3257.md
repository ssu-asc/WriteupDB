# aphelion_vault

## 문제 설명
> Aphelion Vault
>
> Recovered from a Nereid survey relay.
>
> Files:
> - aphelion_vault: Linux x86_64 ELF
>
> Goal:
> - Recover the vault's archive key.
> - Submit the value in the format uctf{...}.
>
> Notes:
> - The binary runs locally and prompts for an alignment phrase.
> - Standard Linux reverse engineering tooling is sufficient.

## 풀이

### 분석

압축을 풀면 `aphelion_vault` 바이너리 하나와 README만 들어있다. `file`로 확인해보니 stripped된 64bit x86_64 ELF라 심볼이 하나도 안 남아있었다. 일단 실행부터 해보니 "alignment phrase"를 입력받는 형태였다.

```
Nereid aphelion vault maintenance client
Recovered handshake requires the correct alignment phrase.
Alignment phrase:
```

적당히 아무거나 넣어보면 "Trajectory rejected." 하고 끝나서, 결국 Ghidra로 디컴파일해서 로직을 봐야 했다. entry point를 따라가면 `FUN_004010c0` 하나가 사실상 전체 로직(입력 받기 + 검증 + 출력)을 다 담당하고 있었다.

디컴파일 결과를 천천히 읽어보면 흐름이 이렇다.

1. `fgets`로 최대 0x80바이트 입력을 받고 개행 제거.
2. `strlen() == 0x18` (정확히 24글자)이어야 통과.
3. 입력 각 글자가 `0x21 ~ 0x7e` (출력 가능 ASCII) 범위인지 검사하면서 동시에 스택의 `local_e8` 위치로 그대로 복사 (변환 없이 그냥 복사본).
4. 바이너리 안에 있는 상수 블롭(나중에 보니 커스텀 섹션 `.vault`, `objdump -S`로는 안 보이고 `readelf -S`로 섹션 리스트를 봐야 나옴)을 가지고 XOR/뺄셈/회전 조합으로 3개의 "타겟 배열"을 그 자리에서 계산.
5. 입력 복사본을 세 그룹(각 8바이트)으로 나눠서, 각 그룹마다 XOR + 덧셈 + 1비트 또는 2비트 또는 3비트 회전(rotate)을 거친 값을 방금 계산한 타겟 배열과 비교. 하나라도 틀리면 "Trajectory rejected." 후 종료.
6. 세 그룹 모두 통과하면 "Vault alignment accepted." 출력하고, 원본 입력 24바이트를 인덱스로 순환 참조하면서 또 다른 상수 블롭과 XOR/덧셈/회전을 섞어 32바이트를 만들어 `puts`로 출력. 이게 곧 플래그였다.

즉 이 문제는 입력값 자체가 미리 정해진 "정답 문자열"이고, 검증 로직은 그 정답 문자열을 회전+XOR로 인코딩한 것과 바이너리에 박힌 상수를 비교하는 구조였다. 회전은 전부 가역 연산(ROL/ROR은 서로 역함수)이고 XOR/덧셈도 상수만 알면 되돌릴 수 있으니, 굳이 브루트포스 안 하고 역산으로 바로 입력을 복원할 수 있겠다 싶었다.

### 상수 위치 찾기

디컴파일 코드에서 `&DAT_004020c0`, `&DAT_004020e0` 두 개의 심볼 없는 전역 데이터를 참조하고 있었는데, `objdump -s -j .rodata`로는 이 주소가 안 잡혔다. `readelf -S`로 전체 섹션을 나열해보니

```
[15] .vault    PROGBITS  00000000004020c0  000020c0  0000000000000040
```

이렇게 별도로 `.vault`라는 커스텀 섹션이 있었다. (챌린지 제작자가 재미로 넣은 이름인 듯. RE 문제에서 종종 보이는 트릭이라 그냥 넘어갔다.) 여기서 64바이트를 덤프하면 앞 32바이트가 검증용 상수(`DAT_004020c0`), 뒤 32바이트가 최종 플래그 인코딩용 상수(`DAT_004020e0`)였다.

### 검증 로직 3그룹 분석

디컴파일 결과를 변수 하나하나 따라가면서 스택 레이아웃을 손으로 그려봤다(로컬 변수 오프셋만 보고는 헷갈려서 실제로 종이에 `-0x128`부터 `-0x30`까지 순서대로 적어봄). 입력 복사본이 저장되는 `local_e8`(8바이트) + `local_e0`(24바이트, 앞 16바이트만 사용)가 사실 하나로 이어진 24바이트 버퍼라는 걸 확인하고 나니 그룹 경계가 명확해졌다.

- **그룹 1 (input[0:8])**: `target1[i] = D[i+4] XOR (0xa5 - 9*i)`. 검증식은 `ROL1((input[i] XOR (0x21+0xd*i)) + (3+7*i)) == target1[i]`.
- **그룹 2 (input[8:16])**: `target2[i]`는 `D[i+12]`를 이용해 계산. 검증식은 `ROL2((input[8+i] + 0x14 + (3+i) + input[(3+i)&7]) XOR (0x5a-3*i)) == target2[i]` — 여기서 `input[(3+i)&7]`은 이미 그룹 1에서 복원된 값이라 순서대로 풀면 된다.
- **그룹 3 (input[16:24])**: `target3[i]`는 `D[i+20]`을 이용해 계산. 검증식은 `ROL3((input[15-i] XOR input[16+i]) + 0x33 + 5*i) == target3[i]` — `input[15-i]`는 그룹 2까지 복원된 값이라 역시 순서대로 풀린다.

세 그룹 다 회전 연산의 역(오른쪽 회전)을 취하고, 앞에서부터 순서대로 대입하면 24바이트 입력을 전부 복원할 수 있는 구조였다. 이걸 파이썬으로 그대로 옮겨서 계산했다.

```python
A = [(D[i+4] ^ ((0xa5 - 9*i) & 0xff)) & 0xff for i in range(8)]
for i in range(8):
    key = (0x21 + 0xd*i) & 0xff
    add = (3 + 7*i) & 0xff
    P[i] = ((ror(A[i], 1) - add) & 0xff) ^ key
```

나머지 두 그룹도 같은 식으로 역산해서 돌려보니 `nereid-apsis-vector-4912`라는, 문제 배경(Nereid, 해왕성의 위성 이름) 이랑 딱 맞아떨어지는 문자열이 나왔다. 얼추 맞는 것 같아서 실제 바이너리에 넣어봤다.

```
$ echo "nereid-apsis-vector-4912" | ./aphelion_vault
Nereid aphelion vault maintenance client
Recovered handshake requires the correct alignment phrase.
Alignment phrase: Vault alignment accepted.
uctf{n3r31d_4ps1s_v4ult_4l1gn3d}
```

바로 통과하고 플래그가 출력됐다.

### 최종 플래그 인코딩

인증에 성공하면 원본 24바이트 입력 문자열(변환 없는 raw 값)을 `idx = n % 24`로 순환 인덱싱하면서, 두 번째 상수 블롭 `E[]`와 XOR하고 위상이 다른 인덱스(`(7+5*n) % 24`)에서 뽑은 값을 1비트 회전시켜 다시 XOR하는 방식으로 32바이트를 뽑아낸다. 이 부분은 입력을 역산할 필요 없이 그냥 정방향으로 계산하면 되는 부분이라 어렵지 않았다.

```python
for n in range(32):
    idx = n % 24
    target = E[n] ^ key_byte
    mixed = (P[idx] + add) & 0xff
    rot_src = P[rot_idx % 24]
    fb = mixed ^ target ^ rol(rot_src, 1)
```

## 플래그
```
uctf{n3r31d_4ps1s_v4ult_4l1gn3d}
```

## 배운 점

- `objdump -s -j .rodata`처럼 이름으로 섹션을 지정하는 방식에 의존하면, 문제 제작자가 커스텀 섹션 이름(`.vault` 같은)에 상수를 숨겨둔 경우 놓칠 수 있다. `readelf -S`로 전체 섹션 테이블을 먼저 훑어서 주소 범위에 뭐가 걸리는지 확인하는 습관이 필요하다.
- 검증 로직이 ROL/ROR + XOR + 덧셈처럼 전부 가역 연산으로만 구성되어 있으면, 브루트포스나 심볼릭 실행 없이도 상수 방향에서 역으로 계산해서 바로 정답 입력을 복원할 수 있다. 다만 이때 각 바이트의 의존 관계(어떤 그룹이 어떤 그룹의 결과를 참조하는지)를 정확히 파악하는 게 핵심이었다 — 순서를 잘못 잡으면 아직 안 풀린 값을 참조하게 되어 막힌다.
- 스택 변수가 많고 포인터가 여러 개 겹쳐서 재사용되는 디컴파일 코드는, 오프셋을 손으로 나열해서 실제 메모리 레이아웃을 그려보는 게 제일 확실했다. Ghidra가 자동으로 이름 붙여준 `local_XX` 변수만 보고 판단하면 겹치는 영역을 놓치기 쉽다.
