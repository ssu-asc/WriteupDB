# Compiled Source Sheets

## 문제 설명

> My new VM is Spectre-proof! It's also guaranteed race-condition free, and runs on every major OS[1]. Try it out!
>
> [1] that supports Chrom(e|ium)

`handout/vm.html` 하나만 제공됨 (폰트 파일 두 개 포함, 782KB짜리 단일 HTML).

## 풀이

### 분석

파일을 열어보니 타이틀이 `x86CSS`. 처음엔 이름 그대로 받아들이지 않고 "설마 진짜 CSS로 CPU를 만들었겠어, JS가 어딘가 숨어있겠지" 하고 `<script>` 태그부터 찾아봤는데, 진짜로 CSS 클럭 애니메이션 하나 말고는 JS가 없었다. `info-box` 섹션을 읽어보니 실제로 존재하는 오픈소스 프로젝트([rebane2001/x86css](https://github.com/rebane2001/x86css))였다. GCC로 컴파일한 8086 기계어를 CSS의 `@property`, `if()`, `@container style()` 같은 최신 Chromium 전용 기능만으로 완전히 에뮬레이션하는 물건. 문제 설명의 "Spectre-proof / race-condition free / runs on every major OS[1] [1] that supports Chrom(e|ium)"이 이 프로젝트를 가리키는 농담이었던 것.

즉 이 문제는 "CSS를 리버싱"하는 게 아니라, **CSS 안에 인코딩된 x86 기계어를 추출해서 평범하게 리버싱**하면 되는 문제다. 관건은 그 기계어(=에뮬레이터의 RAM 초기값)가 어디에 박혀있는지 찾는 것.

레지스터/메모리 셀 하나하나가 CSS custom property 하나에 대응되는 구조라, 계산 로직(`--m0: calc(if(...))` 같은 것들)과 초기값(`@property --m0 { initial-value: ... }`)이 분리되어 있었다. `grep`으로 훑어보니:

```css
@property --m0 {
  syntax: "<integer>";
  initial-value: 204;
  inherits: true;
}
```

이런 블록이 `--m0`부터 쭉 이어졌다. 인덱스를 전부 뽑아서 정렬해보니 `0 ~ 1535`가 연속(=0x600, info-box에 적혀있던 "기본 메모리 크기 0x600바이트"와 일치), 그 뒤로 `8192~8207`, `8448~8463` 두 구간이 더 있었는데 이건 화면/키보드용 메모리 매핑 I/O 영역으로 보여서 프로그램 코드와는 무관하다고 판단하고 무시했다.

레지스터 쪽도 같은 방식으로 초기값이 박혀있어서 확인해보니:

```css
@property --IP { initial-value: 256; }  /* = 0x100 */
```

info-box에 "The program gets loaded at memory address 0x100"이라고 명시되어 있었으니 IP=256과 정확히 일치. 여기가 진입점이라는 확신이 섰다.

### 풀이 과정

1. `--m0` ~ `--m1535`의 `initial-value`를 정규식으로 전부 추출해서 1536바이트 바이너리로 덤프.
2. `capstone`으로 `0x100`부터 16-bit real mode 코드로 디스어셈블. 바로 `push si / push di / push bp / mov bp, sp / sub sp, 0xe` 같은 멀쩡한 함수 프롤로그가 나와서 주소를 제대로 짚었다는 걸 확인.
3. 초반부는 getchar/putchar 루프로 최대 10글자를 스택 버퍼(`bp-10`~`bp-1`)에 입력받는 코드였고, 그 뒤로 입력 길이가 8 이하 & 짝수여야 통과하는 체크, 이어서 버퍼의 앞 8바이트(`buf[0..7]`)에 대해 xor/and/or/cmp를 엮은 검증 체인이 21개 정도 나왔다. 예를 들면:
   ```
   dl = buf[6]; ah = buf[2]; al = dl ^ ah; cmp al, 0x6f  ; je / else fail
   dh = buf[3]; cl = buf[7]; test dh, cl                 ; (dh & cl) == 0 이어야 계속 진행
   ...
   ```
4. 통과 시 출력되는 문자열들을 메모리에서 바로 읽었다 (`gaslight`, `CTF{ch3c`, `k_0ut_ly`, `ra-horse`, `!!_`, 그리고 입력 버퍼 자체, 마지막에 `}`). 이어붙이면 플래그의 앞뒤 껍데기가 그대로 나온다 — 가운데 8글자만 채우면 되는 구조.
5. 21개 제약식을 손으로 다 풀기는 귀찮아서, capstone 디스어셈블리를 보고 각 바이트를 `b0..b7`로 이름 붙여 레지스터 흐름을 그대로 옮긴 뒤 `z3`에 XOR/AND/OR 제약으로 통째로 넘겼다. 풀이는 유일했고 (`b6^b0==4`, `b3&b0==0x30` 같은 식들이 서로 얽혀 있어서 자유도가 거의 없었다), 나온 값은 `2QY90H6F`.
6. 혹시 몰라서 z3가 뱉은 값을 다시 파이썬으로 명령어 순서 그대로 재현(시뮬레이션)해서 21개 조건을 전부 `assert`로 재검증 — 트랜스크립션 실수 여부까지 확인하고 넘어갔다.

최종적으로 문자열 조립:

```
"gaslight" + "CTF{ch3c" + "k_0ut_ly" + "ra-horse" + "!!_" + "2QY90H6F" + "}"
```

## 배운 점

- CSS만으로 튜링 완전한 8086 에뮬레이터를 만드는 게 실제로 가능하다 (`@property` + `if()` + `@container style()` 조합). 문제를 처음 열었을 때 "이게 리버싱 문제 맞나" 싶었는데, 결국 핵심은 에뮬레이터 자체가 아니라 그 안에 로드된 프로그램이었다.
- 이런 "특이한 런타임에 프로그램을 임베드"하는 형태의 문제는, 런타임 자체를 이해하려 하기보다 **런타임의 초기 상태(레지스터/메모리)를 어떻게 소스에서 읽어낼 수 있는지**부터 찾는 게 지름길이었다. `@property ... initial-value`처럼 선언적으로 박혀있는 값은 정규식 한 방으로 전부 추출 가능하다.
- xor/and/or가 뒤섞인 다변수 제약 체인은 손으로 풀지 말고 바로 z3에 넘기는 게 훨씬 빠르고 안전하다 (실수로 부호/자리 하나 잘못 옮겨적어도 unsat으로 바로 티가 남). 다만 최종 값은 반드시 원본 로직을 그대로 재현해서 재검증하는 습관을 들이는 게 좋다.
