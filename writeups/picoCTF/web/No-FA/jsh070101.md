# 문제명
NO-FA
## 문제 설명

> Seems like some data has been leaked! Can you get the flag?

- http://foggy-cliff.picoctf.net:63427/

## 풀이

문제를 처음 실행했을 때는 일반적인 로그인 페이지가 나타났다. 문제에서 users.db 파일이 함께 제공되었기 때문에 먼저 데이터베이스 안에 어떤 정보가 들어있는지 확인해 보기로 했다.

처음에는 SQLite가 무엇인지도 몰라서 검색해 보니, SQLite는 별도의 서버 없이 파일 하나로 데이터를 저장하는 데이터베이스라는 것을 알게 되었다. 그래서 DB Browser for SQLite 프로그램을 설치하여 users.db 파일을 열어보았다.

users 테이블에는 다음과 같은 정보가 저장되어 있었다.

username : admin
email    : iamadmin@nfs.com
password : c20fa16907343eef642d10f0bdb81bf629e6aaf6c906f26eabda079ca9e5ab67
two_fa   : 1

처음에는 마지막 two_fa가 무엇인지 몰라 검색해 보니, 2FA(Two Factor Authentication)는 비밀번호 외에 추가 인증을 한 번 더 수행하는 보안 기능이라는 것을 알게 되었다. 값이 1인 것으로 보아 관리자 계정은 2단계 인증이 활성화되어 있다는 것을 예상할 수 있었다.

다음으로 비밀번호 해시를 확인하였다. 길이가 정확히 64자리의 16진수 문자열이었기 때문에 SHA-256 해시가 아닐까 생각했고 검색해 보니 SHA-256의 출력 길이가 64자리라는 것을 확인할 수 있었다.

문제의 첫 번째 힌트는 다음과 같았다.

What happens when there's no salt?

처음에는 salt가 무엇인지 몰라 검색해 보니, 비밀번호를 해시하기 전에 랜덤한 값을 추가하는 보안 기법이라는 것을 알게 되었다. salt가 없으면 같은 비밀번호는 항상 같은 해시가 생성되므로 사전 공격(Dictionary Attack)이 가능하다는 설명을 확인하였다.

두 번째 힌트인

rockyou rockyou rockyou

를 보고 rockyou.txt라는 유명한 비밀번호 사전 파일을 사용하는 문제라는 것을 알게 되었다.

그래서 Python으로 SHA-256 해시를 계산하면서 rockyou.txt의 비밀번호를 하나씩 비교하는 간단한 스크립트를 작성하였다.

import hashlib

target = "c20fa16907343eef642d10f0bdb81bf629e6aaf6c906f26eabda079ca9e5ab67"

with open("rockyou.txt", encoding="latin-1") as f:
    for pw in f:
        pw = pw.strip()
        if hashlib.sha256(pw.encode()).hexdigest() == target:
            print("FOUND:", pw)
            break

실행 결과 관리자 비밀번호는 다음과 같았다.

apple@123

관리자 계정으로 로그인에는 성공했지만 이번에는 OTP(일회용 비밀번호)를 입력하라는 화면이 나타났다.

처음에는 4자리 OTP를 브루트포스로 모두 시도해 보려고 생각하였다. 하지만 코드를 자세히 읽어보니 OTP는 로그인할 때마다 새로 생성되고 120초 동안만 유효하도록 구현되어 있었다.

otp = str(random.randint(1000, 9999))
session['otp_secret'] = otp
session['otp_timestamp'] = time.time()

여기서 session['otp_secret']이라는 코드가 눈에 들어왔다.

처음에는 session이 서버에 저장되는 것으로 생각했지만, Flask의 session이 어디에 저장되는지 검색해 보니 기본 Flask에서는 session 정보가 서버가 아니라 사용자의 쿠키(Cookie)에 저장된다는 것을 알게 되었다.

브라우저 개발자 도구(F12)를 열어 Application → Cookies를 확인해 보니 실제로 session이라는 쿠키가 존재하였다.

다만 쿠키 값은 다음과 같이 알아보기 어려운 문자열이었다.

처음에는 암호화된 문자열인 줄 알았지만, "Flask session decode"를 검색해 보니 Flask 기본 세션은 암호화가 아니라 서명(Signature) 만 되어 있으며, 내용 자체는 디코딩하여 읽을 수 있다는 설명을 확인하였다.

그래서 Flask Session Decoder를 이용하여 session 쿠키를 디코딩하였다.

디코딩 결과는 다음과 같았다.

{
    "logged": "false",
    "otp_secret": "3936",
    "otp_timestamp": 1784618460.7386982,
    "username": "admin"
}

OTP 값이 그대로 저장되어 있는 것을 확인할 수 있었고, 해당 값을 OTP 입력창에 입력하여 관리자 인증을 완료하였다.

인증이 끝난 뒤 메인 페이지로 이동하였고 관리자에게만 출력되는 Flag를 획득할 수 있었다.

### 취약점

이 문제의 핵심 취약점은 OTP를 Flask Session에 저장한 것이었다.

처음에는 Session은 서버에 저장되는 것으로 알고 있었지만, Flask의 기본 Session은 클라이언트 쿠키에 저장된다는 점을 검색을 통해 알게 되었다.

또한 Flask Session은 암호화(Encryption) 되는 것이 아니라 서명(Signature) 만 되기 때문에 사용자가 내용을 읽는 것은 가능하다.

즉,

session['otp_secret'] = otp

처럼 OTP와 같은 중요한 정보를 Session에 저장하면 사용자가 자신의 쿠키를 디코딩하여 OTP를 그대로 확인할 수 있다.

OTP는 원래 사용자의 이메일 등 별도의 안전한 경로로만 전달되어야 하지만, 이 문제에서는 쿠키 안에 그대로 저장되어 있었기 때문에 2단계 인증이 사실상 무력화되었다.

## 배운 점

이번 문제를 통해 처음으로 salt가 없는 SHA-256 해시는 사전 공격에 취약할 수 있다는 점을 배웠다. 또한 rockyou.txt와 같은 비밀번호 사전 파일을 이용하면 실제 비밀번호를 복구할 수 있다는 것도 알게 되었다.

가장 인상 깊었던 부분은 Flask의 기본 Session이 서버가 아니라 클라이언트 쿠키에 저장된다는 점이었다. 처음에는 Session이 서버에 저장되는 줄 알고 있었지만, Flask에서는 쿠키에 저장되며 암호화가 아니라 서명만 되어 있기 때문에 내용을 읽을 수 있다는 사실을 이번 문제를 통해 처음 알게 되었다.

또한 2단계 인증은 단순히 OTP를 사용하는 것만으로 안전한 것이 아니라, OTP를 어디에 저장하고 어떻게 전달하는지가 매우 중요하다는 점도 배울 수 있었다. 민감한 정보를 클라이언트가 읽을 수 있는 위치에 저장하면 2FA를 구현하더라도 보안 효과가 사라질 수 있다는 것을 이해하게 되었다.
