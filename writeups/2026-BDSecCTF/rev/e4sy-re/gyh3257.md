# e4sy_RE

## 문제 설명
> An easy RE challenge for you. Crack it.
> Flag Format : BDSEC{s0mething_here}

## 풀이

### 분석

`e4sy_RE.bdsec`는 stripped 되지 않은 64bit PIE ELF 바이너리다. `main` 함수를 Ghidra로 디컴파일해보면 `fgets`로 입력을 받은 뒤 입력 길이(`strcspn` 결과)에 따라 4개의 서로 다른 분기로 나뉘어 각각 다른 방식으로 입력을 변환하고, 하드코딩된 `expected_0` ~ `expected_3` 바이트 배열과 비교하는 구조였다.

| 입력 길이 | 비교 대상 | 성공 메시지 |
|---|---|---|
| 0x18 (24) | `expected_0` | "Congratulations! You found a flag!" |
| 0x1a (26) | `expected_1` | "Congratulations! You found a flag!" |
| 0x1d (29) | `expected_2` | "Congratulations! You found a flag!" |
| 0x29 (41) | `expected_3` | "Excellent work, reverse engineer!" |

즉 실제로는 4개의 서로 다른 "플래그 후보" 검증 루틴이 한 바이너리 안에 공존하는 구조였고, 그중 실제 플래그 포맷(`BDSEC{...}`)에 맞는 것을 골라내야 했다.

비교 루틴들은 SIMD 스타일로 벡터화되어 `_DAT_00102xxx ^ auVarN | ...` 형태로 XOR-OR 폴딩을 하는 것처럼 보이지만, 실제로 `_DAT_00102460/70`, `_DAT_00102490`, `_DAT_001024a0`, `_DAT_001024b0` 상수들을 `objdump -s -j .rodata`로 덤프해보면 각각 `expected_3[0:32]`, `expected_2[0:16]`, `expected_1[0:16]`, `expected_0[0:16]`와 완전히 동일한 값이었다. 즉 이 벡터 연산은 단순히 "변환된 입력 == expected_N" 비교를 난독화한 것에 불과했다.

각 분기의 변환 로직을 정리하면 다음과 같다 (모두 바이트 단위, mod 256 연산).

- **0x18 (24바이트)**: 상태 기반 스트림 암호. `state=0x6b`에서 시작해 `state = ROL8(state + (input[i] ^ (0x55+0x11*i)), 3)`, `output[i] = state`.
- **0x1a (26바이트)**: `state = 0x3d+7*i`로 입력을 XOR한 뒤 `ROR8(_, i%5+1)`로 회전시키고, `(i*5) % 26` 위치로 스캐터(치환)하여 저장.
- **0x1d (29바이트)**: `salt[i] = 0x21+3*i`를 입력에 더한 뒤 `ROL8(_, 2) ^ 0xa7`.
- **0x29 (41바이트)**: `input[i] ^ key_part_a_5[i&7] ^ key_part_b_4[i&7]`를 구해 `ROL8(_, i%7+1)`한 값에 `((11*i)&0xff) ^ 0x23`을 더하고, `(13*i) % 41` 위치로 스캐터.

모든 변환은 각 라운드에서 입력 1바이트 → 출력 1바이트로 전단사(역연산 가능)이고, 스캐터 위치 함수(`5x mod 26`, `13x mod 41`)도 계수가 각각 모듈러스와 서로소이므로 역치환이 존재한다. 따라서 `expected_N`으로부터 브루트포스 없이 바로 입력을 역산할 수 있었다.

### 풀이 과정

1. `objdump -s -j .rodata`로 `expected_0` ~ `expected_3`, `key_part_a_5`, `key_part_b_4`, 그리고 각 `DAT_00102xxx` 상수를 전부 덤프.
2. `_DAT_00102xxx` 상수들이 `expected_N`의 앞부분과 동일함을 확인 → 벡터 비교가 사실상 `output == expected_N` 임을 검증.
3. 4개 분기 각각에 대해 순방향 연산의 역함수(회전 반대 방향, 뺄셈, XOR, 역치환)를 Python으로 구현.
4. 4개 후보를 모두 복원한 결과:
   - 0x18 → `CFLAG{y0u_f0uNd_4_d3c0Y}` (디코이)
   - 0x1a → `BFLAG{r3v3rS1ng_1s_4n_4rT}` (디코이)
   - 0x1d → `AFLAG{n1c3_trY_bUt_n0_p01nTs}` (디코이)
   - 0x29 → `BDSEC{e4SY_r3v3rS3_eNg1N33r1nG_cH4LL4ng3}` ← 문제에서 요구하는 `BDSEC{...}` 포맷과 일치
5. 실제 바이너리에 해당 문자열을 입력해 `[+] Excellent work, reverse engineer!` 메시지로 검증 완료.

```python
$ echo "BDSEC{e4SY_r3v3rS3_eNg1N33r1nG_cH4LL4ng3}" | ./e4sy_RE.bdsec
...
[+] Excellent work, reverse engineer!
[+] Submit the flag to the CTF platform to receive your points.
```

## 배운 점
- 하나의 바이너리에 여러 개의 검증 분기(디코이 플래그 포함)를 심어 놓는 유형은, 문제에서 제시된 플래그 포맷(prefix/구조)으로 정답 분기를 선별하는 것이 핵심이다.
- 컴파일러/Ghidra가 SIMD로 자동 벡터화한 비교 코드는 겉보기엔 복잡해 보여도, 관련 상수(`_DAT_xxx`)를 실제로 덤프해서 원본 `expected` 배열과 대조해보면 단순 바이트 비교로 환원되는 경우가 많다.
- 각 바이트 변환이 XOR/덧셈/회전처럼 전단사 연산으로만 이루어져 있고 상태(state)가 이전 출력값에만 의존하는 경우, 브루트포스 없이 `expected` 값으로부터 직접 역산이 가능하다. 스캐터형 인덱스(`k*i mod n`)는 모듈러 역원을 구해 치환을 되돌리면 된다.
