# funk

## 문제 설명
> 파일 하나(`funk`)만 주어짐. 문제 설명 없이 순수 brainfuck 소스 파일.

## 풀이

### 분석

`file funk` 해보니 그냥 "ASCII text, with very long lines"로 나온다. 열어보면 `+-<>[],.` 만으로 이루어진 28785바이트짜리 brainfuck 소스였다. `tr -d '<>+-.,[]'` 했을 때 남는 글자가 없는 걸로 순수 BF라는 것도 재차 확인.

문자 카운트부터 찍어봤다.

```
+ : 8376   - : 5273   > : 7461   < : 7376
[ : 126    ] : 126    , : 38     . : 9
```

`,`가 38개니까 입력을 최대 38바이트까지 받는 것 같고, `.`이 9개뿐이라 출력은 거의 없을 걸로 예상. 일단 아무 문자열이나 넣고 표준 BF 인터프리터로 돌려봤는데 — 순수 파이썬 인터프리터로는 끝날 기미가 안 보였다. `[`/`]` 매칭마다 딕셔너리 룩업하는 방식이 너무 느려서, BF를 파이썬 소스코드로 "컴파일"하는 방식으로 바꿨다. `+-<>` 연속된 구간은 카운트로 묶어서 한 줄로, `[...]`는 그냥 파이썬 `while` 문으로 그대로 옮기는 방식. 이러면 인터프리팅 오버헤드가 거의 사라진다.

컴파일해서 빈 입력으로 돌려보니 즉시 무한루프에 빠졌다. 소스 맨 끝을 보면:

```
...>>>>>>>>>>>>>>>>>>>>>>>>>>>>>>>>>>>>>>>>>>>>>>>>>>>>>>>>>>+[]
```

`+` 하나 찍고 빈 루프 `[]`로 끝난다. 조건 셀에 `+`를 무조건 한 번 하기 때문에 (255였다가 오버플로우로 0 되는 경우가 아닌 이상) 이 루프는 성공/실패 상관없이 항상 걸리는 "종료용 무한루프"라고 판단했다. 그래서 다른 입력을 넣어도 항상 이 마지막 루프에서 멈추는 게 정상 동작이고, 문제는 "여기서 멈췄는지"가 아니라 "멈추기 전에 뭔가 출력이 있었는지"로 성공 여부를 봐야 한다는 뜻이었다.

스텝 제한을 걸어서(3,000,000 반복이면 진짜 무한루프인지 충분히 판별 가능) 어디서 멈추는지 확인하는 하네스를 만들고, 빈 입력/`A`*38 두 가지로 돌려봤다. 둘 다 `,` 31번 읽고 마지막 루프에서 멈췄고, 출력은 0바이트. 흥미로운 건 두 경우 다 **정확히 같은 지점**에서 멈춘다는 것 — 즉 입력이 틀려도 프로그램이 어디선가 다른 곳으로 새서 트랩에 빠지는 구조가 아니라, 항상 같은 코드 경로를 타면서 어딘가의 "결과 값"만 달라진다는 뜻이다.

그래서 각 `[...]`에 진입 횟수 카운터를 붙였다 (126개 루프 전부). 빈 입력으로 한 번 돌려서 baseline 카운트를 뽑고, 이번엔 38바이트 입력 중 딱 한 자리만 임의의 값(111)으로 바꿔가며 baseline과 diff를 떴다.

결과가 아주 깔끔했다: 0~30번 자리(31자리)가 각각 **정확히 하나의 루프**에만 영향을 줬고, 그 루프의 반복 횟수는 항상 `(baseline_count + input_byte) mod 256` 이었다. 즉 `[-<->]` 같은 형태의 "값 이동" 루프였고, 그 반복 횟수 자체가 그 시점 셀의 값이었던 것. baseline_count는 입력과 무관하게 고정된 상수(그 위치의 "목표값의 보수" 같은 값)였다.

여기서 가설: 이 이동 루프가 0번 도는 게 "정답"이다. 즉 `input_byte = (256 - baseline_count) % 256`.

31자리 전부 계산해서 넣어봤다.

### 풀이 과정

1. brainfuck을 파이썬 함수로 컴파일 (루프당 hit counter 포함)
2. 빈 입력으로 baseline 실행 → 각 위치가 어떤 loop id에 매핑되는지, 그 loop의 기본 카운트가 뭔지 뽑기
3. `input_byte[i] = (256 - base_count[i]) % 256` 로 31바이트 복원
4. 복원한 문자열을 실제로 넣어서 재검증 — 해당 31개 루프가 전부 0번 실행되는지 확인
5. 확인 후, 한 글자만 ±1 흔들어서 대응 루프 카운트가 딱 1로만 바뀌고 나머지는 그대로인지 재확인 (서로 독립적인 체크라는 것, 그리고 우연이 아니라는 것 확인용)

4번, 5번 다 통과해서 이 문자열이 맞다고 확신했다. (참고로 이 프로그램 자체는 맞는 입력을 넣어도 따로 "Correct!" 같은 걸 출력하진 않는다 — 체크 로직만 존재하고 출력 부분은 죽은 코드였던 것 같다. 그래서 알고리즘적으로 복원한 값을 그대로 플래그로 제출.)

## 배운 점
- brainfuck처럼 순수 인터프리팅이 느린 esolang을 다룰 땐 "BF → 파이썬 while문"으로 컴파일해버리면 표준 인터프리터보다 훨씬 빠르게 돌릴 수 있다. `+-<>` 연속 구간을 카운트로 묶는 것만으로도 체감 속도 차이가 크다.
- 무한루프로 끝나는 BF 프로그램을 볼 때, "루프에 걸렸다 = 실패"라고 바로 단정하지 말고 그 트랩이 입력에 관계없이 항상 도달하는 지점인지부터 확인해야 한다. 여기서는 파일 맨 끝의 `+[]`가 그냥 프로그램 종료용 관용구였다.
- 값 하나 바꿔가며 나머지 상태(여기선 각 루프의 반복 횟수)와 diff 떠보는 건 블랙박스 바이너리 분석에서 쓰는 타이밍/사이드채널 기법이랑 똑같은 아이디어다. BF 루프 하나의 "도는 횟수"가 그 시점 셀 값 그대로 노출되는 걸 이용해서, 실제 산술 로직(수백 개의 `+`/`-`가 뒤섞인 난독화된 덧셈 체인)을 전혀 읽지 않고도 정답을 복원할 수 있었다.
