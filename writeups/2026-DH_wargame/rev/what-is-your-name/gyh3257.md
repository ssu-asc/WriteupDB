# What is your name?

## 문제 설명
> 실수로 exe 파일을 너무 많이 만들어버렸어요!
> 수많은 exe를 분석해 플래그를 획득해 주세요!

압축 파일을 풀면 이름이 이상하게 생긴 exe 11개가 나온다. (`AEx.exe`, `2^j.exe`, `]]{.exe` 같은 식으로 3글자 파일명 + 확장자)

## 풀이

### 시도 1 — 그냥 실행/문자열 검색

리눅스 환경이라 바로 실행이 안 돼서 `wine`부터 찾아봤는데 설치가 안 되어 있었다. (`which wine` 실패)

그래서 일단 제일 만만한 `strings`부터:

```
$ strings -n 6 2^j.exe | grep -iE "flag|DH{|dreamhack"
```

아무것도 안 나온다. `file`로 찍어보니 전부 `PE32+ executable (console) x86-64` 에 사이즈까지 123392바이트로 완전히 동일. 파일명만 다른데 내용물이 다 똑같다는 게 말이 안 되니, 실제로는 내부에 미묘한 차이가 있을 거라 생각하고 `cmp -l`로 바이너리 diff를 떠봤다.

### 시도 2 — 파일 간 diff로 차이점 찾기

```
$ cmp -l "2^j.exe" "2^q.exe"
  1109  11   4
```

첫 번째 파일을 기준으로 나머지 10개와 전부 diff 떠보니 (`cmp -l 2^j.exe *.exe`), 매번 **offset 1109** 한 곳이 무조건 다르고, 일부 파일은 **offset 113153**도 같이 다르다는 걸 확인했다. 이 두 오프셋을 11개 파일 전부에 대해 뽑아봤다:

| 파일 | offset 1109 | offset 113153 |
|---|---|---|
| AEx.exe | 01 | 03 |
| Ng^.exe | 02 | 01 |
| Dgj.exe | 03 | 02 |
| 2^q.exe | 04 | 01 |
| 2\`c.exe | 05 | 01 |
| ^\`m.exe | 06 | 01 |
| b]u.exe | 07 | 02 |
| pgr.exe | 08 | 02 |
| 2^j.exe | 09 | 01 |
| mnv.exe | 0a | 01 |
| ]]{.exe | 0b | 02 |

offset 1109 값이 1~11(0x01~0x0b)로 정확히 겹치는 것 없이 다 나뉘어 있는 걸 보고 "이게 순서(인덱스)구나" 싶었다. offset 113153 쪽은 1, 2, 3 세 종류만 나오는 걸 보고 처음엔 "그룹 번호인가?" 했는데, 확실히 하려면 실제로 이 바이트들이 코드/데이터 어디에서 쓰이는지 봐야 했다.

### 시도 3 — pefile + objdump로 실제 로직 확인

`pefile` 모듈을 깔아서 (venv에 이미 있길래 재사용) 섹션 레이아웃을 뽑아봤다:

```python
import pefile
pe = pefile.PE('2^j.exe')
print(hex(pe.OPTIONAL_HEADER.AddressOfEntryPoint))
for s in pe.sections:
    print(s.Name, hex(s.VirtualAddress), hex(s.PointerToRawData), hex(s.SizeOfRawData))
```

`.text`가 파일 오프셋 `0x400`부터 시작하니, offset 1109(0-index 1108)는 `.text` 안 RVA `0x1054` 근처였다. `objdump -d -M intel`로 해당 부근을 까봤다:

```
140001047: mov QWORD PTR [rsp+0x28],rax        ; PathFindFileNameA 결과 저장
14000104c: lea rcx,[rip+0x122ad]        # 0x140013300   ; "index %d : " 포맷 문자열
140001053: mov edx,0x9                                    ; <- 여기가 offset 1109!
140001058: call 0x1400010c0                               ; printf(fmt, 9)
```

`0x140013300`의 데이터를 `pe.get_data()`로 읽어보니 문자열이 `"index %d : "` 였다. 즉 offset 1109는 **"이 exe가 몇 번째인지" 알려주는 인덱스**였던 것.

그 다음 루프를 계속 따라가니:

```
140001075: movsx eax, BYTE PTR [rax+rcx*1]     ; filename[i]
140001079: cmp eax, 0x2e                        ; '.' 이면 루프 종료
14000108f: movsx ecx, BYTE PTR [rax+rcx*1]      ; filename[i] 다시 로드
140001093: add ecx, DWORD PTR [rip+0x1bf67]     # 0x14001d000  <- 여기가 아까 그 두번째 offset!
140001099: call 0x140002f20                     ; putchar류 출력
```

정리하면: 자기 자신의 실행 파일명(`GetModuleFileNameA` → `PathFindFileNameA`)을 읽어서, `.`(확장자 구분자) 전까지 한 글자씩 `0x14001d000`에 있는 상수값을 더해서 출력하는 구조. offset 113153이 바로 이 `0x14001d000` 위치의 상수(1~3)였다.

즉 파일명 자체가 암호문이고, 프로그램은 "자기 이름"에 Caesar shift를 적용해서 진짜 글자를 뱉어내는 구조. 문제 제목 "What is your name?"이 그대로 힌트였던 셈.

### 풀이 과정

11개 파일에 대해 (인덱스, key, 확장자 제외 파일명)을 뽑아서 `chr(ord(c) + key)`로 복원하고 인덱스 순서대로 이어붙이면 된다.

```python
import pefile, struct, glob

order, key = {}, {}
for fn in sorted(glob.glob('*.exe')):
    pe = pefile.PE(fn)
    rva_order = 0x1000 + (1108 - 0x400)   # offset 1109 (0-idx 1108) -> .text RVA
    n = struct.unpack('<i', pe.get_data(rva_order, 4))[0]
    k = struct.unpack('<i', pe.get_data(0x1d000, 4))[0]   # shift key
    order[n] = fn.split('.exe')[0]
    key[n] = k

flag = ''
for i in range(1, 12):
    name, k = order[i], key[i]
    flag += ''.join(chr(ord(c) + k) for c in name)

print(flag)
```

실행 결과:

```
1 AEx  key=3  -> DH{
2 Ng^  key=1  -> Oh_
3 Dgj  key=2  -> Fil
4 2^q  key=1  -> 3_r
5 2`c  key=1  -> 3ad
6 ^`m  key=1  -> _an
7 b]u  key=2  -> d_w
8 pgr  key=2  -> rit
9 2^j  key=1  -> 3_k
10 mnv key=1  -> now
11 ]]{ key=2  -> __}

FULL: DH{Oh_Fil3_r3ad_and_writ3_know__}
```

1번(`AEx.exe`, key=3)이 바로 `DH{`로 풀리는 걸 보고 방향이 맞다는 확신이 들었다.

## 플래그
```
DH{Oh_Fil3_r3ad_and_writ3_know__}
```

## 배운 점
- 겉보기에 완전히 동일해 보이는 다중 바이너리 문제는 `cmp -l`로 바이트 단위 diff부터 떠보면 차이 나는 offset을 빠르게 좁힐 수 있다.
- `GetModuleFileNameA` + `PathFindFileNameA`로 "자기 자신의 파일명"을 읽어 로직에 활용하는 패턴 — 파일명 자체가 문제의 일부(암호문)가 될 수 있다는 점을 유의.
- `pefile`로 섹션별 RVA ↔ 파일 오프셋 변환을 해두면 objdump 디스어셈블 결과와 원본 파일의 raw byte diff를 정확히 대조할 수 있다.
- 여러 프로그램에 흩어진 "순서 인덱스 + 개별 파라미터(shift key)" 조합으로 플래그를 분산시키는 문제 유형은, 각 바이너리를 개별 실행하는 것보다 정적으로 상수만 추출해서 스크립트로 조립하는 게 훨씬 빠르다.
