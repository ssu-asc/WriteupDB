# lykn-corp

## 문제 설명

Welcome to our company's internal system. We have just launched a new Onboarding portal for new employees.The system looks very safe and secure, but is it really?

## 풀이

### 분석

처음 접속하면 `LYKN Mail`이라는 내부 메일 시스템 로그인 화면이 나온다.

로그인 정보가 없으므로 먼저 기본적인 정보 수집을 진행했다.

```text
/robots.txt
```

에 접근하면 다음과 같은 내용이 나온다.

```text
User-agent: *
Disallow: /backup
```

`/backup` 경로가 존재한다는 힌트를 얻을 수 있다. 하지만 직접 접근하면 `403 Forbidden`이 발생한다.

```text
/backup -> 403 Forbidden
```

여기서 중요한 점은 `/backup`이 단순히 존재하지 않는 경로가 아니라, 존재하지만 접근이 막힌 경로라는 것이다.

이후 경로 대소문자를 바꿔보며 접근을 시도했다.

```text
/Backup/
```

그 결과 디렉터리 접근이 가능했고, 내부 파일을 추측하여 다음 경로에 접근할 수 있었다.

```text
/Backup/credentials.txt
```

응답에는 신규 직원 계정 정보가 포함되어 있었다.

```text
New Employee Credentials
========================
Username: tuan.nguyen
Password: Welcome123!
```

해당 계정으로 로그인하면 `Tuan Nguyen`의 메일함에 접근할 수 있다.

메일함에는 온보딩 관련 메일이 하나 있었고, URL 구조는 다음과 같았다.

```text
/email/1
```

여기서 메일 ID가 숫자로 직접 노출되어 있으므로 IDOR 가능성을 의심할 수 있다.

다른 메일 ID를 직접 접근해보면 일반 사용자가 볼 수 없어야 할 메일에 접근할 수 있었다.

```text
/email/2
```

해당 메일에는 다른 직원 또는 관리자 관련 민감 정보가 포함되어 있었다.

특히 `Minh Le` 계정으로 접근한 후 `/email/2`에서 다음과 같은 관리자용 서비스 계정을 확인할 수 있었다.

```text
Username: admin
Password: Adm1n_S3cur3_P@ss_2026
```

이 계정을 이용해 관리자 또는 모니터링 대시보드에 접근하여 최종 플래그를 획득할 수 있다.

### 취약점

이 문제에는 여러 취약점이 연쇄적으로 사용된다.

1. 정보 노출

`robots.txt`에 민감한 백업 경로가 노출되어 있었다.

```text
Disallow: /backup
```

`robots.txt`는 보안 장치가 아니라 크롤러에게 수집하지 말라고 알려주는 파일이다. 따라서 민감한 경로나 백업 경로를 여기에 적어두면 오히려 공격자에게 힌트를 주게 된다.

2. 대소문자 우회 / 경로 설정 오류

`/backup`은 `403 Forbidden`이었지만 `/Backup/`은 접근 가능했다.

즉, 접근 제어는 소문자 `/backup`에만 적용되어 있었고, 실제 정적 파일 또는 라우팅 처리는 대소문자 차이를 다르게 처리했다.

```text
/backup  -> 403
/Backup/ -> accessible
```

이로 인해 보호되어야 할 백업 파일에 접근할 수 있었다.

3. 민감 정보가 포함된 백업 파일

`/Backup/credentials.txt`에 실제 로그인 가능한 계정 정보가 저장되어 있었다.

```text
Username: tuan.nguyen
Password: Welcome123!
```

백업 디렉터리나 임시 파일에 계정 정보가 남아 있으면 초기 침투 지점이 된다.

4. IDOR

메일 상세 페이지가 다음과 같이 단순한 숫자 ID 기반이었다.

```text
/email/1
/email/2
```

로그인한 사용자가 해당 메일의 소유자인지 제대로 검증하지 않아, 다른 사용자의 메일도 직접 조회할 수 있었다.

이로 인해 관리자 계정 정보가 포함된 메일까지 읽을 수 있었다.

### 익스플로잇

전체 흐름은 다음과 같다.

```text
1. /robots.txt 확인
2. /backup 경로 발견
3. /backup 접근 시 403 확인
4. /Backup/ 대소문자 우회 시도
5. /Backup/credentials.txt 접근
6. tuan.nguyen 계정 획득
7. 메일 시스템 로그인
8. /email/1 구조 확인
9. /email/2 등 다른 ID 접근
10. 관리자 계정 정보 획득
11. 관리자 기능 또는 대시보드 접근
12. 플래그 획득
```

예시 요청 흐름:

```http
GET /robots.txt HTTP/1.1
Host: target
```

```http
GET /Backup/credentials.txt HTTP/1.1
Host: target
```

획득한 계정:

```text
Username: tuan.nguyen
Password: Welcome123!
```

로그인 후 IDOR 테스트:

```http
GET /email/2 HTTP/1.1
Host: target
Cookie: session=...
```

메일에서 관리자 계정 확인:

```text
Username: admin
Password: Adm1n_S3cur3_P@ss_2026
```

flag{REDACTED}

## 배운 점

이 문제는 단일 취약점 하나로 끝나는 문제가 아니라, 작은 실수들이 연쇄적으로 이어지는 전형적인 웹 침투 흐름을 보여준다.

핵심 단서는 다음과 같았다.

- `robots.txt`의 `/backup`
- `/backup`이 404가 아니라 403이라는 점
- 경로 대소문자 차이
- `credentials.txt` 같은 백업 파일명 추측
- `/email/1`처럼 숫자 ID가 노출된 메일 상세 URL
- 다른 ID 접근 시 권한 검증이 부족한 IDOR

특히 `/backup`에서 바로 막혔다고 끝내는 것이 아니라, `403 Forbidden`은 “경로가 존재한다”는 신호로 보고 우회 가능성을 탐색해야 한다.

또한 인증 이후에는 URL의 숫자 ID, 사용자 ID, 게시글 ID, 메일 ID처럼 직접 참조되는 값이 있으면 반드시 IDOR 여부를 확인하는 습관이 중요하다.
